## 🔍 Faz 3 — Gerçek Test Sonucu

Round-robin scheduler gerçekten çalışıyor — `Tick #1/#2/#3...` şeklinde Task Alpha/Beta arasında düzenli geçiş, Ring 3'e geçiş, `sys_yield`, `sys_sleep` (non-blocking), `sys_exit` + zombie temizliği hepsi log'da doğrulandı. Ayrıca boşta CPU'yu `hlt` ile beklettiğinizi gördüm (`cpu_halt()` ana döngüde) — bu, çoğu hobi kernelin atladığı ama gerçek donanımda enerji/performans açısından kritik bir detay, tebrikler.

### ⚠️ Bulduğum 2 Gerçek Sorun

**1. Küçük ama gerçek bir bug — `user_write` çağrılarında off-by-one:**

Log'da şunu gördüm (görünmeyen ama gerçek bir `\0` byte'ı):
```
[RING 3 USER APP] Hello from Ring 3 User Mode!
␀ [RING 3 USER APP] Executed via int 0x80 Syscall Engine!
```

Sebebini buldum — `usermode_app.c`'de string uzunlukları elle sayılmış ve hepsi **+1 fazla**:
```c
user_write(" [RING 3 USER APP] Hello from Ring 3 User Mode!\n", 49);  // gerçek uzunluk: 48
user_write(" [RING 3 USER APP] Executed via int 0x80 Syscall Engine!\n", 58); // gerçek: 57
```
`sys_write` verilen `len` kadar byte yazıyor (doğru davranıyor), ama `len` string'in null terminator'ünü de kapsayınca, o `\0` byte'ı da serial/VGA'ya basılıyor. Çözüm basit: elle saymak yerine `sizeof(msg) - 1` kullanın (derleme zamanında otomatik hesaplanır, insan hatasına kapalı):
```c
#define USER_WRITE_STR(s) user_write(s, sizeof(s) - 1)
USER_WRITE_STR(" [RING 3 USER APP] Hello from Ring 3 User Mode!\n");
```

**2. Bu, Faz 4'ten önce acilen bakılması gereken bir durum — kernel disk bütçenizin sınırına dayandınız:**

```
kernel.bin boyutu : 30.920 byte
Ayrılan bütçe     : 32.768 byte  (KERNEL_SECTORS=64 × 512)
Kalan pay         : sadece %5.6 (~1.8 KB)
```

`boot.asm`'iniz hem BIOS `INT 13h` diskten okumayı hem de `0x10000→0x100000` kopyalama döngüsünü **sabit 64 sektör** üzerinden yapıyor. Faz 4'te VFS + ATA driver + dosya sistemi eklediğinizde kernel kesinlikle bu sınırı aşacak — ve aşarsa, disk'ten hiç okunmayan/kopyalanmayan kısım **sessizce kesilir**. Bunun sonucu genelde "rastgele bir fonksiyonun ortasında" triple fault olur ve hata mesajınız bile görünmez, çünkü kodun kendisi eksik yüklenmiştir. Faz 4'e başlamadan önce **ilk iş** olarak `KERNEL_SECTORS`'ı örneğin 256'ya (128 KB) çıkarın ve disk imaj boyutunu (`dd count=...`) buna göre büyütün. 5 dakikalık iş ama atlanırsa günler sürecek bir debug kabusuna dönüşebilir.

## 📁 Faz 4 — İsteğinize Göre Şekillendirilmiş Yol Haritası

İstediğiniz 3 şey net: **(1)** Linux gibi "her şey dosyadır" felsefesi, **(2)** başka işletim sistemlerinin okuyabileceği gerçek dosya sistemleri, **(3)** çalışan sistem üzerinde canlı müdahale/inceleme ("açık kalp ameliyatı"). Bunların hepsi aslında **tek bir mimari karar** ile birbirine bağlanıyor: iyi tasarlanmış bir **VFS (Virtual File System) katmanı**. Sıra:

### Adım 4.0 — Güvenlik Önlemi (ACİL, yukarıda anlatıldı)
- `KERNEL_SECTORS` büyütme, disk imaj boyutu güncelleme, `make` ile regresyon testi

### Adım 4.1 — ATA/IDE PIO Disk Sürücüsü
- Artık BIOS yok, gerçek donanım konuşacaksınız: `0x1F0-0x1F7` (Primary ATA) portları üzerinden `IDENTIFY`, `READ SECTORS (0x20)`, `WRITE SECTORS (0x30)` komutları
- Polling tabanlı (IRQ14 ile interrupt-driven versiyonu opsiyonel/ileri seviye — başta polling yeterli)
- Test: `ata_read_sector(0, buf)` ile MBR'nizi (kendi bootloader'ınızı!) okuyup serial'a hex dump basma — kendi diskinizi kendi driver'ınızla okuduğunuzu doğrulama

### Adım 4.2 — VFS Çekirdek Soyutlaması ("Her Şey Dosyadır")
Bu, isteğinizin kalbi. Linux'taki gibi:
- `vnode_t` (Linux'taki `inode`'un karşılığı): `type` (FILE/DIR/DEVICE/PROC), `size`, `read()`, `write()`, `readdir()` fonksiyon pointer'ları (bir çeşit "sınıf" — her FS/device kendi implementasyonunu bu tabloya yazar)
- `mount_t` yapısı — `"/"`, `"/dev"`, `"/proc"` gibi mount noktaları, hangi FS driver'ına bağlı olduklarını tutar
- `vfs_open(path)`, `vfs_read(fd, buf, len)`, `vfs_write(...)`, `vfs_close(fd)`, `vfs_readdir(...)` — path çözümleme (`/dev/serial0` gibi bir string'i doğru mount noktasına ve doğru vnode'a yönlendirme)
- Her `task_t`'ye bir **file descriptor tablosu** ekleme (`int fds[MAX_FDS]`, her biri bir açık vnode'a işaret eder) — `sys_open/sys_read/sys_write/sys_close` syscall'ları artık VFS üzerinden çalışacak (mevcut `sys_write`'ınızı da buraya taşıyabilirsiniz — `stdout` aslında `/dev/console`'a yazan bir dosya olur)

### Adım 4.3 — `devfs` (Sanal, Disksiz Dosya Sistemi) — **İlk VFS Backend'iniz**
Gerçek disk driver'ına bağlı olmadığı için Adım 4.1'le paralel bile yazılabilir:
- `/dev/serial0` → `serial_putchar`'a yazan bir vnode
- `/dev/kbd` → klavye ring buffer'ınızı okuyan bir vnode
- `/dev/null`, `/dev/zero` — klasik Unix cihazları
- Bu adımdan sonra kullanıcı programınız artık `sys_write(1, buf, len)` yerine gerçekten `open("/dev/serial0")` → `write(fd, ...)` yapabilir — Linux'takiyle birebir aynı model

### Adım 4.4 — `procfs` (Canlı Sistem İnceleme) — **"Açık Kalp Ameliyatı" Tam Burası**
İstediğiniz canlı müdahale özelliği doğal olarak buradan geliyor:
- `/proc/tasks` → o an çalışan tüm `task_t`'lerin listesini (PID, state, ESP, EIP) okunduğu anda üretip döndüren bir vnode (statik veri değil, `read()` çağrıldığında **anlık** üretilir)
- `/proc/meminfo` → PMM'den anlık free/used sayfa sayısı
- `/proc/gdt`, `/proc/tss` → daha önce yazdığınız `dump_gdt()`/`dump_tss()` fonksiyonlarını artık serial'a değil, bu sanal dosyalara bağlama
- Bunun gerçek gücü: ileride basit bir shell yazdığınızda, `cat /proc/tasks` demek, çalışan sistemi **durdurmadan** içini görmek demek — gerçek anlamda "açık kalp ameliyatı"

### Adım 4.5 — Gerçek Disk Dosya Sistemi: **FAT16/32**
"Başka işletim sistemleri okuyabilsin" isteğiniz için en doğru seçim kesinlikle **FAT32** — çünkü:
- Windows, Linux, macOS'un **hepsi** yerleşik olarak FAT32 okur/yazar (NTFS okuma karmaşık+lisans riskli, ext2/4 Windows'ta yerleşik değil)
- Belgelenmişliği en yüksek dosya sistemi (osdev.org'da tam spec var)
- Bu FS'i yazınca, ZeruX diskini gerçek bir USB bellek olarak formatlayıp Windows'a takıp içindekileri görebilirsiniz, ya da Windows'ta oluşturduğunuz bir dosyayı ZeruX'ta okuyabilirsiniz — **iki yönlü gerçek interoperabilite**
- Alt adımlar: Boot sector (BPB) parse etme → FAT tablosunu okuma → root directory taraması → cluster chain takip ederek dosya içeriği okuma → (yazma desteği ayrı ve daha riskli bir sonraki adım)

### Adım 4.6 — VFS'e FAT32'yi Bağlama
- `vfs_mount("/", fat32_driver)` — artık `/proc`, `/dev`, ve gerçek disk dosyaları **aynı path ağacında** birlikte yaşıyor, Linux'taki gibi

### Adım 4.7 (Opsiyonel, İleri Seviye) — Çoklu Dosya Sistemi Desteği
"Tüm dosyaları okuyabilsin" hedefine daha da yaklaşmak isterseniz, VFS soyutlamanız zaten hazır olduğu için eklemesi görece kolay olanlar:
- **ISO9660** — CD-ROM dosya sistemi, formatı FAT'tan bile basit, QEMU'da `-cdrom` ile test edilebilir
- **ext2 (salt-okunur)** — Linux disklerini okumak isterseniz, orta zorlukta, iyi belgelenmiş
- **NTFS/exFAT** — gerçekten çok karmaşık (NTFS özellikle), bunları en sona bırakın ya da hiç yapmayın; gerçekçi olmak gerekirse çoğu hobi OS projesi buraya hiç gelmez

### Adım 4.8 — Basit Kabuk (Shell), Artık Gerçek Bir Amaçla
Daha önce sorduğunuz shell konusu tam burada oturuyor: artık `ls /`, `cat /proc/tasks`, `cat /dev/serial0` gibi komutlar çalıştıran bir kabuk yazmak hem test aracınız hem de "gerçek OS" hissinizin zirvesi olur.

ZeruX Architecture Update & Enhancements
This plan outlines the steps to implement the architectural renaming, VFS mount enumeration, MBR partition table integration, and power control commands.

Proposed Changes
1. VFS Mount Enumeration (vfs.c, vfs.h, rootfs.c)
[MODIFY] kernel/include/vfs.h & kernel/fs/vfs.c: Add a vfs_get_mount_info() API to allow querying registered mounts by index.
[MODIFY] kernel/fs/rootfs.c: Update rootfs_readdir to list static directories AND dynamically enumerate directly attached VFS mounts (e.g., /live, /wire).
2. Architectural Path Renaming
[MODIFY] kernel/fs/rootfs.c: Define static directories: /run, /cfg, /app, /user, /core, and /disk.
[MODIFY] kernel/fs/procfs.c: Mount to /live instead of /proc.
[MODIFY] kernel/fs/devfs.c: Mount to /wire instead of /dev.
[MODIFY] kernel/fs/fat32.c: Mount to /disk/fat0 instead of /fat.
[MODIFY] kernel/drivers/shell.c: Update help menu and boot demo commands to use the new paths (ls /wire, ls /live, ls /disk/fat0).
3. Shell Power Commands (shell.c, ports.h)
[MODIFY] kernel/drivers/shell.c: Add reboot command utilizing the 8042 Keyboard Controller reset pulse (outb(0x64, 0xFE)).
[MODIFY] kernel/drivers/shell.c: Add shutdown command utilizing QEMU's ACPI shutdown port (outw(0x604, 0x2000)).
4. MBR Partition Table (boot.asm)
[MODIFY] bootloader/boot.asm: Reserve the final 64 bytes before the boot signature (offset 0x1BE) for a standard MBR Partition Table.
Inject a partition entry for the FAT32 volume: Type 0x0C (FAT32 LBA), Start LBA 256, Size 300 sectors. This allows standard OSes (Linux/Windows) to natively detect and mount the FAT32 volume from the zerux.img.
Open Questions
For the FAT32 mount, does /disk/fat0 work for you, while keeping /disk as a static directory in rootfs? This correctly maps the nested mount point.
The shutdown command will use a QEMU-specific ACPI trick (outw(0x604, 0x2000)). On real hardware, an APM/ACPI driver is required. Is this acceptable for the emulator environment?
Verification Plan
Compile and run the kernel in QEMU.
Run ls / in the shell to verify all new paths (live, wire, disk, run, cfg, etc.) are enumerated correctly.
Test reboot and shutdown commands.
Mount the image in Linux via losetup to verify the partition table is correctly parsed.
